Payments Razorpay (or similar) — server-side verification + webhooks
2. Database Schema
Golden rule: current_balance is never directly writable. Every balance change happens
through a ledger_entries row created by the ledger service. No manual overwrite, ever —
this is what gives you the audit trail.
3. Backend (NestJS) — Modules
villages
  id, name, code, created_at
customers
  id, village_id (FK), name, mobile, address, photo_url, kyc_status, created_at
nominees
  id, customer_id (FK), name, relation, mobile, address
customer_documents
  id, customer_id (FK), doc_type, file_url, verified_status, uploaded_at
customer_bank_details
  id, customer_id (FK), account_number, ifsc, account_holder_name
pigmy_accounts
  id, customer_id (FK), daily_amount, current_balance, total_deposited, status
transactions
  id, pigmy_account_id (FK), amount, gateway_txn_id, status (pending/success/failed), created_at
ledger_entries
  id, pigmy_account_id (FK), transaction_id (FK), type (credit/debit),
  amount, previous_balance, new_balance, created_at
admins
  id, name, email, password_hash, role, assigned_villages
audit_logs
  id, actor_id, actor_type, action, entity, entity_id, before, after, created_at

6. Security Requirements
Balances are derived, never directly editable — enforced at the service layer, not just
UI
Payment verification happens server-side only; client “success” callbacks are never
trusted on their own
Webhook signature verification on every Razorpay callback
Idempotency keys on payment processing (prevent double-crediting on webhook
retries)
Rate limiting on OTP requests
Role-based access control on all admin routes
Every balance-affecting action writes an audit_logs row
